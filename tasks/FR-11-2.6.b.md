## Steps

1. **BLL Domain** — `Domain/Actor` enum (Tourist, Guide, System); `IBookingStateMachine` + `BookingStateMachine` with the 8-row table from CLASSES_SPECS §5: `CanChange` = table lookup; `Apply` = refuse if not allowed, else set `Status` and the matching time field (`RespondedAtUtc` / `CancelledAtUtc` + reason / `CompletedAtUtc`). Data conditions (overlap, deadline) stay in the services of 2.7–3.1. Register Singleton.
2. **BLL validator** — extend `CreateBookingValidator`: a `"Create"` rule set (preview keeps using only the default rules): `StartDate` required; Hourly `StartTime` required and `StartTime + Hours` ≤ end of that day; start ≥ now + `MinAdvanceHours` in the guide's time zone (guide `TimeZoneId` read through injected `IUnitOfWork`, `TimeProvider` for now).
3. **BLL service + mapping** — `BookingMappingProfile`: `CreateBookingRequest → Booking` (ignore price, status, dates, ids). `CreateAsync(touristId, request, ct)`: validate with `"default","Create"` → load guide, `GuideRules.IsBookable` → map → local → UTC (R6) → `PriceCalculator` → `Status = Pending`, `CreatedAtUtc = now` → `AddAsync` + `SaveChangesAsync` → `BookingDto`.
4. **PL** — `Validation/FutureDateAttribute` + adapter in `wwwroot/js/validation.js` (loaded by `_ValidationScriptsPartial`); `CreateBookingViewModel.StartDate` gets `[Required]` + `[FutureDate]`; `BookingsController.Create` POST: `ModelState` → map → `CreateAsync(_currentUser.UserId, …)` → errors back into the form (price box refreshed) or `TempData` success + redirect to `Index`; enable "Send request".
5. **Build + manual check** — `dotnet build`; AC1–AC12 with a $20/h guide.

## Open questions

1. **24 h check and time zone:** the check needs the guide's `TimeZoneId`, which only the DB has. Plan: the validator reads it through injected `IUnitOfWork` (allowed: "data through an injected interface"). Cost: the guide is loaded twice (validator + service). OK, or move only this one check into the service (layer 4)?
2. **Rule set:** the preview must not require a start date. Plan uses a FluentValidation `"Create"` rule set on the same validator (one validator per DTO). OK?
3. **`FutureDate` on the client** only knows the browser's clock and zone, not the guide's. Plan: client check is a rough first filter; the server decides. OK?
4. **Daylight-saving edge:** a local start time that doesn't exist or exists twice (clock change night). Plan: refuse "invalid" times with a field error; take the first of two "ambiguous" times. OK?
5. **Duplicate requests:** same tourist, same guide, same time while one is `Pending`. Not in the docs → plan allows it (the guide decides). Confirm.
